# Armazenamento no navegador na publicação da Vercel

Status: aceita

A Function do ADR 0009 mantinha os dados em memória por instância, o que dava resultados inconsistentes: um cadastro feito numa instância não existia em outra, e tudo voltava à semente a cada cold start. A publicação passa a ser estática: o build (`ARMAZENAMENTO=local npm run build`) copia `public/` e `src/` e `db.json` para `dist/` e grava `modo.js` com `'local'`; nesse modo `recurso(nome)` de `src/shared/api.js` devolve `recursoLocal(nome)` (`src/shared/armazenamento-local.js`), com a mesma interface, que guarda cada coleção no `localStorage` (chaves `aluguel:v1:<colecao>`) e carrega `/db.json` como semente na primeira leitura. Localmente `npm start` segue com o JSON Server e `db.json`, como exige o enunciado, e o `json-server` passa a ser dependência de desenvolvimento. Descartados: banco externo (Upstash Redis, Vercel Blob), por trazer dependência nova fora da stack obrigatória; e manter a Function, por não resolver a inconsistência de dados entre instâncias. Consequências: os dados ficam por navegador, cada visitante vê só os próprios dados e não há compartilhamento entre Cliente e Agente em máquinas diferentes; limpar os dados do site apaga tudo (`restaurarDadosDeExemplo` volta à semente); o limite do `localStorage` (cerca de 5 MB) e seu bloqueio geram `ErroApi` com mensagem clara. O catálogo de automóveis é sincronizado com a semente a cada visita, preservando o proprietário gravado; os demais dados do navegador só recebem a semente na primeira visita. Os services não mudam, pois já usavam `recurso()`.
